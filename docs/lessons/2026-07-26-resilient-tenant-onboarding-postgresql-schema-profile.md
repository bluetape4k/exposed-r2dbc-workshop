# 복구 가능한 테넌트 온보딩 PostgreSQL 스키마 프로필

## 배경

`08-resilient-tenant-onboarding-spring-webflux`는 H2에서 검증하던 테넌트
온보딩 수명주기를 실제 PostgreSQL에서도 실행할 수 있어야 했다. 하나의 데이터베이스를
공유하되 `public.tenant_lifecycle`에는 수명주기를 저장하고,
`tenant_<tenant-id>` 스키마에는 테넌트 자원을 격리하는 방식으로 범위를 정했다.

## 결정

- 기본 프로필은 설치가 필요 없는 `h2`로 유지한다.
- `postgres` 프로필은 공유 `ConnectionFactory`와 PostgreSQL 방언을 사용한다.
- 스키마 생성은 먼저 별도 트랜잭션에서 커밋하고, 준비 테이블 생성과 검증은 이후
  트랜잭션으로 분리한다.
- 신규 온보딩의 `create`와 시작 복구의 `restore`를 분리한다. `restore`는 DDL을
  실행하지 않고 기존 준비 표식만 검증한다.
- 실패한 스키마는 자동 삭제하지 않는다. 수명주기 행과 스키마를 남겨 장애 조사와
  멱등적인 재시도가 가능하게 한다.
- 시작 복구 중 코루틴 취소는 테넌트 장애로 기록하지 않고, 생성한 런타임 자원만
  정리한 뒤 호출자에게 다시 전파한다.

## 구현 중 확인한 점

1. `SpringApplicationBuilder.properties()`로 넣은 값은 프로필 YAML보다 우선순위가
   낮을 수 있다. 컨테이너 접속 정보를 확실히 덮어써야 하는 통합 테스트에서는
   command-line argument로 전달해야 한다.
2. reconciler가 온보딩용 `create`를 재사용하면 누락된 스키마를 다시 만들어
   손상된 `ACTIVE` 상태를 정상처럼 보이게 한다. 복구는 반드시 DDL 없는
   `restore → probe → publish` 순서를 사용해야 한다.
3. Testcontainers 인스턴스를 공유하면서 실패 스키마를 의도적으로 보존하면 고정된
   테넌트 ID가 다음 테스트를 오염시킬 수 있다. 통합 테스트의 테넌트 ID에는 짧은
   무작위 접미사를 붙인다.
4. 스키마 이름은 SQL 식별자다. 테넌트 ID를 그대로 이어 붙이지 말고 별도 값 타입에서
   허용 문자와 PostgreSQL 63바이트 제한을 다시 검증해야 한다.

## 앞으로 지킬 경계

- 연결 풀을 도입하더라도 이전 연결의 스키마 상태를 신뢰하지 않는다. 모든 테넌트
  업무 트랜잭션은 시작할 때 자신의 스키마를 명시적으로 선택해야 한다.
- `ACTIVE`는 현재 프로세스의 레지스트리에 이미 게시됐다는 뜻이 아니라, 영속 자원이
  준비되어 재시작 뒤 다시 검증하고 게시할 수 있다는 뜻이다.
- 자동 스키마 삭제, 분산 잠금, 외부 비밀 관리, 운영용 인증, 다중 노드 제어는 이
  예제의 보장 범위가 아니다.

## 검증

- 모듈 전체 `check`
- 실제 PostgreSQL에서 스키마 생성, 테넌트 격리, 실패 보존과 재시도
- 전체 Spring application context 재시작 뒤 `ACTIVE` 테넌트 재게시
- 누락된 스키마의 `RECOVERY` 실패 전이
- 복구 중 코루틴 취소 전파와 영속 상태 보존
